# c0182863 Mac runtime

Build `c0182863` retains the corrected shared CH0 response bus and registered
host reset, and adds the quantizer predicate timing correction. It provides
JTAG USER2 and PCIe memory/control with an independent 250 MHz host clock.
Compute is 148.837209 MHz, DDR1066.667, capacity 4 GiB. CH0 uses physical lanes
`0,1,2,3,4,5,8,7` without ECC; CH1 retains ECC.

Bitstream SHA256:
`03b513a44544009afff9dfb82515bf84c5df84ac6a63673a0882308ce8a323ae`.
Reviewed image-manifest SHA256:
`143554ed99423f024344a916e5b6c7ee1e53d210a78bfa5d9b534762bd1dbdfb`.

Exact packet/CRC, routing, timing, pin, pad and CDC review passed. All 1,993
non-info CDC rows are accounted for. Setup slack is +0.004 ns and hold slack is
+0.012 ns. External DDR pad timing and physical PCIe/reset reliability remain
unqualified. The final review reused the completed routed evidence after a
receipt-format reader correction; the FPGA was not rebuilt for that correction.

Local SRAM INIT/DONE/IDCODE, live USER2 identity with PCIe absent, CH0 calibration
preserving CH1 and the fresh exact-image ISA oracle passed. Required full-memory
initialization, the 1,371-instruction fetch check with 65 exact output words and
int8 matmul with 32 exact output words also passed. Trained TinyStories passed:
all 28,909,056 model bytes and SHA256 read back exactly, all 15 program readback/
load checks passed, and all eight physical tokens matched the ISA. Calibration
was unchanged. Three 64 MiB native-read runs passed at median 4.452533 GB/s
from FPGA counters, with final 16 KiB comparisons. This is synthetic combined-
channel throughput, separate from PCIe transfer bandwidth and Qwen decode
bandwidth. The local JTAG client/server exited
zero and the hardware lease was verified free. See the small
[local validation receipt](../runtime/c0182863/local-validation.json).
Permanent programming, independent verification, JTAG-requested flash boot and
live identity also passed on October 18; see the
[separate flash closure](../build/hardware/flash-c0182863-20261018T125114Z/closure.json).
This does not establish cold power-cycle repeatability or today's card identity.

On the Mac, this exact image subsequently passed LFM2.5-230M and Qwen3.5-2B
INT8 eight-token comparisons against fresh ISA. The matched Qwen benchmark
used 94.2% of 4 GiB and measured 31.36 device prefill tok/s, 7.73 device decode
tok/s and 15.38 GB/s while decoding. All 137 program readbacks passed; ECC
counters stayed clean and calibration was unchanged. See the
[Mac benchmark and comparison record](data/spare_pcie_benchmark_c0182863_20261018.json).
Wall decode was 8.0% slower than c0182800 in this one pass; host conditions and
the cause of that regression were not controlled or isolated.

The [current evidence and outstanding-test table](bitstreams.md#tested-builds-and-outstanding-tests)
also records later source/module-simulation findings in this exact image's
compiled bridge: simultaneous accepts publish a Gray counter change from 0 to 3,
and a six-bit pending count can wrap at 64 and release reset while commands
remain queued. These findings do not invalidate the recorded physical workload
passes, but the unchanged c0182863 bitstream has no correction for these corners.
They were not newly observed Mac hardware failures. Older hash-bound programming
metadata that says Mac qualification is pending predates the Mac results above;
it is retained as historical evidence.

## Initialization time and progress

The LFM test initializes all 4 GiB and verifies the zeros before native matmul
and inference. The existing FPGA BIST engine performs both passes; the Mac
sends register commands and reads counters rather than transferring 8 GiB of
zero data over USB. The host serializes 2,048 operations of 4 MiB each and
waits 200 ms after every operation. Those deliberate pauses alone total
409.6 seconds (6 minutes 49.6 seconds), before command, polling and memory
execution time. A higher compute clock does not shorten the fixed pauses.

The matching LFM runner prints validated chunk counts, percentage, elapsed
seconds, channel and write/verify phase. While it runs, the output directory
contains `lfm/zero-initialization-chunks.jsonl`; each line is a validated chunk
and its progress. `lfm/manifest.json` updates `zero_initialization_progress`
after the first chunk and every 16 chunks. Failed or interrupted runs preserve
their partial journal and any collected failed-chunk counters. Reaching 2,048
validated chunks alone is insufficient: the final readiness check and the
initialization marker must also succeed before `initialization_complete`
becomes true. Output files belong to this run's `SPARE_OUT` directory.

This reporting update preserves the 4 MiB operations, 200 ms pauses, whole-
range verification, ECC guards and exact program/token comparisons. It needs
updated host source on the Mac, with no reflash or bitstream transfer. An
already running process continues using the source it imported at startup;
let it finish before updating and use a fresh output directory for a rerun.

The historical pacing reduced average test activity; it was not a measured
hardware minimum or a bound on peak current. Reducing gaps or increasing chunk
sizes needs a controlled physical comparison before becoming the default.
Automatic calibration in a successor image is separate from whole-memory
initialization and does not remove these host delays by itself. Faster
initialization has not yet been physically qualified. The Qwen benchmark can
reuse a complete initialization receipt after checking the live initialization
marker, exact runtime binding, unchanged calibration and idle compute. The
LFM acceptance path deliberately forces a fresh initialization.

The host runner also has an explicit pacing experiment. The default remains
200 ms. After a baseline LFM run completes, use a fresh output directory to
try 20 ms with the same flashed c0182863 card and checkpoint:

```bash
SPARE_OUT="build/mac-c0182863-pause20-$(date -u +%Y%m%dT%H%M%SZ)" \
  SPARE_EXPERIMENTAL_INIT_PAUSE_MS=20 bash tools/mac_spare_c0182863.sh lfm
```

Allowed values are 0, 5, 20, 50 and 200 ms; other stages reject this setting
before opening hardware. The experiment retains all 2,048 operations, full
zero read verification, counter/lane checks, final readiness, initialization
marker, matmul, program readbacks and exact ISA tokens. Each manifest records
`zero_initialization_policy`, including the selected gap and planned pause
total. For 20 ms the planned pauses total 40.96 seconds; actual elapsed time
also includes commands, polling and memory execution. This is an unqualified
experiment, with no claimed startup improvement until physical results pass.
Compare elapsed initialization and full LFM receipts, unchanged calibration,
clean ECC and exact tokens against the default run on the same image. Keep
failed receipts; do not promote faster pacing from elapsed time alone. A
running process and other image-specific host packages retain their imported
policy. These host changes require no reflash.

## Permanent flashing requires JTAG

**Chestnut alone cannot program this image.** It provides PCIe runtime access;
the c0182800 and c0182863 designs do not expose a configuration-flash controller
through PCIe. Their JTAG runtime memory interfaces also require a physical JTAG
connection. Transferring `otpu.mcs` does not change the running FPGA image.

Connect a compatible JTAG programmer, such as the Xilinx DLC10 / Platform Cable
USB II, to the powered card's JTAG header. The recorded programming path uses
Vivado Hardware Manager on a Linux or Windows JTAG host. With a Mac connected
only through Chestnut, use that JTAG host to program the card, then reconnect
it to the Mac for runtime tests. Native macOS programming has not been qualified
by this handoff. Keep the working c0182800 artifact as the fallback.

### Check the transferred file on the Mac

Set the actual location of the file you transferred:

```bash
export SPARE_MCS=/absolute/path/to/otpu.mcs
shasum -a 256 "$SPARE_MCS"
```

The result must be
`ce318208e248992fd3ae37d3682f44096937db13c989e2376f21ce0228aef0d4`.
The file is 36,200,992 bytes. Check that same checksum on the JTAG host before
programming. For Windows PowerShell, use `Get-FileHash -Algorithm SHA256`.

### Program, independently verify and boot with Vivado

These steps write permanent configuration flash. Stop all card workloads and
other JTAG clients first, and retain the programmer's logs. Use the already
reviewed c0182863 MCS above; a fresh FPGA build is not needed.

1. Power the card, connect its JTAG programmer to the programming host, and open
   **Vivado Hardware Manager → Open Target → Auto Connect**. Confirm the target
   is the XC7K480T. The recorded raw silicon IDCODE is `0x23751093`.
2. Right-click the FPGA and choose **Add Configuration Memory Device**. Select
   exactly **`mt28gu512aax1e-bpi-x16`**: Micron, 512 Mbit, parallel x16.
3. Choose **Program Configuration Memory Device** and select the transferred
   `otpu.mcs`. Use the file's address range, BPI RS pins **none**, and unused-pin
   termination **pull-none**. Enable **Erase**, **Program** and **Verify**;
   leave blank-check and checksum disabled. Accept loading the flash-access
   core into FPGA SRAM. It temporarily replaces the running OpenTPU design.
4. Let erase/program/verify finish without interrupting power or JTAG. Require
   successful completion with no programming or verification errors.
5. Run the configuration-memory operation again with **Erase** and **Program**
   disabled and **Verify** enabled. This is the separate verification pass;
   keep its result independently from the programming result.
6. Right-click the FPGA and choose **Boot from Configuration Memory Device**.
   Wait at least ten seconds, refresh the device and check both INIT and DONE.
   In the Vivado Tcl console, with this FPGA selected, the checks are:

   ```tcl
   set dev [current_hw_device]
   refresh_hw_device -update_hw_probes false $dev
   get_property REGISTER.IR.BIT4_INIT_COMPLETE $dev
   get_property REGISTER.IR.BIT5_DONE $dev
   ```

   Both must report true/1. Close the hardware target and release the JTAG
   client after recording the result.
7. Power the card off and back on to check cold boot, then connect Chestnut on
   the Mac and run the identity check below before calibration or inference.
   Program/verify, requested flash boot, cold boot, live identity and LFM are
   separate results.

The configuration-memory dialog and boot operation are documented in AMD's
[programming guide](https://docs.amd.com/r/en-US/ug908-vivado-programming-debugging/Programming-a-Configuration-Memory-Device)
and [flash-boot instructions](https://docs.amd.com/r/en-US/ug908-vivado-programming-debugging/Booting-the-FPGA-Device).
The exact part, BPI settings and separate verification sequence above match the
recorded local programming workflow.

Do not pass this Vivado MCS directly to the existing generic
`program.sh --flash` / openFPGALoader path. Its BPI writer performs its own byte
conversion, and its sampled verification is not the complete separate
verification used here. That alternate Mac path needs its own qualification.

The matching runtime files are published on `ypcb/dual-channel-4gb` in commit


The live identity must report `c0182863`, 148.837 MHz compute, DDR1066 and 4 GiB.
If the card still reports c0182800, use that image's runtime helper; the MCS
transfer has not qualified or changed the running image.

A power cycle after programming restores fresh CH1-only startup calibration.
The matching helper then calibrates CH0 while preserving CH1. The LFM command
checks live identity, initializes memory, compares matmul and runs LFM against
the ISA reference. Every program must read back exactly before its IMEM load.
A mismatch preserves expected/actual bytes and withholds execution.

Keep all receipts, including failures, under `SPARE_OUT`. Use a fresh output


It measures native device counters and compares the final 16 KiB, separately

## Compare the same Qwen3.5-2B workload

After a successful fresh c0182863 LFM run, keep the same powered configuration
and reuse its calibration and initialization receipts:

```bash
"$SPARE_PYTHON" tools/benchmark_spare_c0182863.py \
  --calibration-receipt "$SPARE_OUT/calibration/manifest.json" \
  --initialization-receipt "$SPARE_OUT/lfm/manifest.json" \
  --out build/mac-c0182863-qwen35-2b-1
```

This uses the same INT8 checkpoint, 4096-token cache, resident decode, 512-token
Austen prompt and 32 decode steps as the c0182800 benchmark. It verifies eight
tokens against ISA and reads back every program before loading IMEM. Device
timing uses the live reported compute frequency. Wall timing includes host/USB
work and full-logit readback. A power cycle requires fresh calibration and
initialization; older-boot receipts are rejected. Preserve all results,
including failures. The recorded October 18 c0182863 pass used this command
and matched the c0182800 checkpoint, configuration and 32 benchmark token IDs;
it is a separate measured run, not a controlled clock-only A/B.

To investigate host overhead, add `--profile-host` and select another fresh
output directory. The optional `host_profile` section records phase intervals
and elapsed call time for transport reads/writes/polling, board program
verification/loading, backend execution and engine compilation/future waits.
The same matmul, ISA tokens and program readback requirements still apply.

```bash
"$SPARE_PYTHON" tools/benchmark_spare_c0182863.py --profile-host \
  --calibration-receipt "$SPARE_OUT/calibration/manifest.json" \
  --initialization-receipt "$SPARE_OUT/lfm/manifest.json" \
  --out build/mac-c0182863-qwen35-2b-profile-1
```

`board.load_program` includes the write, exact readback, receipt writes and
IMEM-load completion. `engine._take` can include waiting for a compile future;
`backend.read` includes result/logit reads. Inclusive timings contain nested
calls. Self timings remove profiled child calls on the same thread. Threads
can overlap, and a call is assigned to its phase at entry, so neither sum is
a partition of benchmark wall time or CPU time. Inspect the matching phase
and device counters together. Profiling itself adds overhead: compare like
profiled runs before attributing a difference. It is off by default and
does not change clock settings, buffers, polling policy or correctness gates.
The source instrumentation alone does not identify the cause of the recorded
wall-decode regression.
